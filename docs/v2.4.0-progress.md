## Recovery and autosave batch, implemented by Claude Code

Claude Code implemented this batch directly on `develop/v2.4.0` under equal
co-developer authority, starting from `a04e7c8`.

### Delivered

- One bounded recovery slot at `relayConsole.recovery.v1`. Never a history: a
  new capture replaces the previous one.
- Capture immediately before restart, saved-relay discard, and an imported
  session replacing existing work. Empty relays are skipped entirely.
- Seven-day expiry, evaluated on read. Expired or unusable records are removed
  the moment they are seen rather than lingering until a timer fires.
- A one-megabyte serialized ceiling. An oversize relay is refused whole, nothing
  is truncated, and the alert points the user to Save file.
- Restoration runs through `validateSession`, so a hand-edited recovery record
  is treated exactly as cautiously as an imported file.
- Visible Restore and Remove controls in a bar that sits outside both the setup
  and run panels, so it survives the switch between them. Remove is confirmed.
- An autosave status line with the last successful local save time. The
  timestamp never advances on a failed save, and a failure stays visibly failed
  until a save succeeds.
- A storage report in the presets panel covering the total plus the session,
  presets, and recovery slots, with quota guidance that names the specific
  controls to use when space runs short.
- Complete English, French, and Spanish copy, including a privacy note stating
  that discarded or replaced work can remain in local storage for up to seven
  days unless removed.

## Claude Code audit of the peer-hardening batch

Claude Code audited every change from `620bc2f` through `71d21c1` by executing
the artifact, not by reading the patch. Ten of ChatGPT's eleven corrections held
up exactly as described. Four defects were found and fixed directly.

### Defects found and corrected

1. **A pending restore consumption could delete an unrelated checkpoint.**
   `consumeRecoveryOnSave` was a bare boolean. A restore whose autosave failed
   armed it, and it then survived both Restart and Remove, so the next ordinary
   successful autosave deleted whatever checkpoint existed by that point.
   Reproduced twice: once where Restart had just captured a fresh copy of the
   very relay being protected, and once where a later unrelated capture was
   destroyed. Both paths lost user work permanently. The flag is now
   `consumeRecoveryAt`, holding the `savedAt` of the record the restore came
   from, and a save consumes the slot only when the stored record still matches.
   A new capture and a manual Remove both disarm it.

2. **A backward clock correction destroyed a valid checkpoint.** The
   future-date rejection had zero tolerance, so a record one millisecond ahead
   of the clock was refused, and `refreshRecoveryOffer` then deleted it. An
   ordinary NTP correction, a virtual machine resume, or a dual-boot clock
   mismatch was enough to lose a good checkpoint. A one-day skew allowance is
   now tolerated, well inside the seven-day window, while a genuinely bogus date
   is still rejected.

3. **Two different units in the same panel.** `recoverySize` measured UTF-8
   bytes through `Blob` while `Store.usage` measured UTF-16, so a checkpoint
   that had just passed a one-megabyte ceiling was displayed as 2.00 MB in the
   storage report beside it. Both now use one `storageBytes` helper measuring a
   conservative two bytes per JavaScript code unit. Actual quota accounting is
   implementation-defined, so the figure remains explicitly labeled as an
   estimate. The tradeoff is that the effective ceiling halves in character
   terms, which is the safe direction and keeps the two app surfaces consistent.

4. **The storage report was recomputed on every keystroke.** It had been wired
   into `saveSetupDraft`, `savePref` and `persistRoster`, all of which fire per
   character. Measured at seven `localStorage` reads and roughly 400,000
   characters re-read for a single keystroke with a large prior session stored.
   All three now route through a coalescing `scheduleStorageReport`, so a burst
   of typing costs one measurement instead of one per character.

### Confirmed working as described

- Restore keeps its checkpoint while autosave fails and consumes it on the first
  save that succeeds.
- The one-megabyte boundary is exact: the largest fitting relay saves and one
  character more is refused with nothing stored.
- Focus after Remove lands on the answer field during a relay, the Resume button
  when a saved session is offered, and the question field otherwise. Focus after
  Restore lands on the answer field.
- Confirmation ordering during restart and discard, the failed-write choice, the
  oversize cancel path, empty-work skipping, and expiry all behave as claimed.

## Claude Code reciprocal audit of the recovery edge cases

Claude Code audited `8844c13..ce48dc4` by executing the artifact. Every claim in
that range reproduced.

### Confirmed

- The surviving D1 variant is genuinely closed on both continuation paths. With
  a restore whose autosave failed and a Restart whose replacement write then
  fails, the older checkpoint survives the continuation and survives a later
  successful save. The same holds when the replacement is refused for being
  oversize.
- Declining the continuation correctly keeps the pending consumption armed, so
  the restored workflow still consumes its own checkpoint on the next good save.
- Exact-record identity is a real improvement over `savedAt`. A record written
  in the same millisecond by another tab is preserved, which the timestamp
  comparison could not guarantee. A byte-identical rewrite is still consumed,
  which loses no distinct work.
- A stale in-memory offer restores older content but never deletes the newer
  record in storage, so no work is lost by that race either.
- The deterministic timer queue is accurate. Three rapid writes schedule exactly
  one 500 ms measurement and the callback measures exactly once.

### Corrected

The timer queue upgrade had one side effect worth closing. Deferring
`setTimeout` means the app's five other deferred callbacks no longer execute
during the suite at all, where the previous synchronous stub at least ran them.
A throwing callback could pass unnoticed. A new test now drains every pending
callback and asserts none throws, and it also asserts the one visible outcome
the suite had never checked: the preset status auto-clear and its sequence
guard, including that an older timer cannot clear a newer message.

ChatGPT's verification tightened that new test so it creates and asserts all
five callback families directly: prompt-copy status, mini-copy reset, object-URL
cleanup, import-dialog focus return, and preset-status clearing. It now checks
the exact timer delays plus every visible outcome, rather than assuming that
callbacks from uncalled paths were already pending. The suite remains at 205
checks because the existing test was strengthened rather than supplemented.

### Residual notes, neither worth a change

- `captureBeforeDestructive` disarms a pending consumption even when it returns
  `skipped`. Unreachable in practice, because the only calls made while a
  consumption is pending pass a session that has meaningful work. Either
  behaviour is lossless.
- `restoreRecovery` reads the cached in-memory offer rather than re-reading
  storage, unlike the preset import path which re-derives. Confirmed lossless:
  the newer record survives. Worth aligning only if recovery ever gains a second
  slot.
